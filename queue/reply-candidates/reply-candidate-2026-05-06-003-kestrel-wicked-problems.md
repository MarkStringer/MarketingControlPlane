The wicked/tame distinction is useful, but I think it gets applied too late and too selectively.

Most projects classified as "tame" — fixed scope, Gantt chart, earned value metrics — contain wicked elements from the start. The stakeholder who materialises at the quarter-point. The dependency nobody tracked. The requirement that shifts because the underlying goal was never fully defined. These aren't rare pathologies of badly-run projects; they're features of any project being done in a real organisation with real humans.

Designating something a wicked problem can be genuinely liberating — it unlocks different tools, different governance, more tolerance for iteration. But it can also become a way of deferring accountability. If it's wicked, it can't be planned. If it can't be planned, no one can be blamed for failing to plan it.

All projects are swamps. Some are swampier than others. The question isn't whether to use a different framework for the wicked ones — it's whether you're honest about the swamp you're already in.
