## Draft

The moment a stakeholder describes a project, something strange happens: they start treating the description as if it *is* the product.

A diagram. A spec. A slide deck. A confident sentence in a meeting.

None of these are the thing. They are the biscuit tin, not the biscuit. And no matter how detailed the picture on the lid, the tin doesn't taste like a biscuit.

This matters because a lot of project pain flows directly from this confusion.

When people mistake the description for the product, they expect the real software to match the original idea — exactly. Same features. Same scope. Same timeline. No surprises.

But software projects don't work that way. They involve uncertainty, discovery, complexity, and changing conditions. The map is never the territory.

So when the reality arrives — different, partial, slower, messier — it feels like failure. Even when it isn't.

The more useful question isn't "does this match the original idea?" It's "does this deliver real value to real people?"

Some features, delivered well, to the people who actually need them, are worth more than every feature, delivered poorly, to the fantasy user you imagined six months ago.

That shift — from exact-match thinking to asymmetrical thinking — is harder than it sounds. But it's the difference between delivering the fantasy and delivering the possible.
