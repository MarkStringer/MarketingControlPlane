## Draft

A description of a biscuit is not a biscuit.

A picture of a biscuit is not a biscuit.

A detailed specification of a biscuit — its exact dimensions, its ingredients, the precise distribution of chocolate chips — is still not a biscuit.

Only the biscuit, in the world, in your hand, is the biscuit.

We all know this. And yet software projects routinely operate as if a thorough enough spec is nearly the same as working software. As if a roadmap is nearly the same as a shipped product. As if having agreed what we want is nearly the same as having it.

This is what I call 'exact match' thinking. The assumption that a description can stand in for the thing itself — that if we write it down carefully enough, we've basically done it.

It's not laziness. It's how symmetrical thinking works. We imagine the project, and the imagined project *feels* real. Stakeholders start treating it as if it already exists. Timelines feel like formalities. Change feels like betrayal.

Working software breaks the spell. When people can actually use something — however incomplete, however rough — the biscuit tin falls away and the actual biscuit appears.

Deliver something. Anything real. Before the map becomes the territory.
